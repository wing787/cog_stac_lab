# COG の部分読み出しを転送量で検証する

**問い**: 「COG にすると部分読み出しできて転送量が減る」と言うが、実際に何バイト減るのか。
速度でなく**バイトとリクエスト数**で答える。クラウドでは egress 課金とラウンドトリップが
コストと体感を決めるため。

対象は合成ラスター（6000×6000, UInt16, 滑らかな地形風パターン, 72MB 無圧縮）。
実業務データは使わず、誰でも同じ数字を再現できるようにしている。

## 0. 出発点の誤解を正す

作業前の理解は「読み込み時に bbox を指定すれば、関心範囲の外を読まずに済む」だった。
**結論は正しいが、理由が抜けていた**。

- 素の GeoTIFF にも窓は指定できる（`gdal_translate -srcwin` / `-projwin`）。
  geotransform（左上原点 + ピクセルサイズ）があるので地理 bbox → ピクセル窓の変換はいつでも可能。
- 問題は「その窓がファイル内で**何バイトに散っているか**」。
  素の GeoTIFF の多くは **strip**（N行 × **画像の全幅**）単位で並ぶ。

```
strip レイアウト : Block=6000x1  ← 全幅 x 1行
COG (tiled)      : Block=512x512 ← 2次元ブロック
```

strip では窓が**行方向にしか刈られず、列方向は全幅引かれる**。
512×512 の窓を読むのに `512行 × 6000px × 2byte = 6,144,000 バイト` が必要になる。

実測 6,160,384 バイト（GDAL が 16KB 境界に切り上げるぶんだけ理論値より多い）。
**理論値と実測が一致**したので、この理解は正しい。

## 1. 空間軸 — 内部タイル化

同じ 512×512 の窓（`-srcwin 3000 3000 512 512`）を読む。

| ファイル | GET | 転送量 |
| --- | ---: | ---: |
| strip（無圧縮） | 4 | 6.210 MB |
| COG 無圧縮 | 3 | 2.114 MB |
| COG + LZW（既定） | 3 | 1.392 MB |
| COG + LZW + PREDICTOR=2 | 3 | 0.249 MB |
| COG + ZSTD + PREDICTOR=2 | 3 | 0.184 MB |

### 罠: 窓の「位置」でも転送量が変わる

`3000 ÷ 512 = 5.86` で窓がタイル境界に整列していないため、**2×2 = 4 タイル**にまたがる。

| 窓の起点 | COG 無圧縮 | COG ZSTD+PREDICTOR | strip |
| --- | ---: | ---: | ---: |
| 3000, 3000（非整列） | 2.114 MB ≒ 4 タイル | 0.184 MB | 6.210 MB |
| 3072, 3072（整列） | 0.557 MB ≒ 1 タイル | 0.082 MB | **6.210 MB（変わらず）** |

**タイルは部分読みの最小単位**。1バイト欲しくても 1 タイル丸ごと転送される。
GeoParquet の row-group が最小単位なのと同じ構造で、クラウド最適化フォーマット共通の骨格。

strip 版だけ整列しても転送量が変わらないのは、**列方向の刈り取りがそもそも存在しない**ため。
タイル化して初めて「窓の位置」という変数が意味を持つ。

## 2. 解像度軸 — overview

bbox だけでは説明できない軸。「全域をズームアウトして俯瞰する」問い（`-outsize 750 750`）は
空間的には**全タイルが対象**なので、bbox では一切刈れない。

| ファイル | GET | 転送量 |
| --- | ---: | ---: |
| strip | **645** | 28.738 MB |
| COG 無圧縮 | 2 | 2.130 MB |
| COG + LZW（既定） | 2 | 1.180 MB |
| COG + LZW + PREDICTOR=2 | 2 | 0.410 MB |
| COG + ZSTD + PREDICTOR=2 | 2 | 0.262 MB |

COG は `3000x3000, 1500x1500, 750x750, 375x375` の overview を内蔵するので、
**750×750 の版を読むだけ**で済む（4タイル × 0.524MB ≒ 2.10MB が無圧縮版の内訳）。

strip 側が 645 リクエストに膨らむのは、8行おきの間引き読みのたびに 16KB 単位の
チャンクを取りに行く**読み取り増幅**が起きるため。欲しいのは 9MB 相当なのに 28.7MB 引いている。

> **リクエスト数は転送量とは別のコスト**。S3 では 645 × RTT がそのまま体感速度になり、
> GET リクエスト課金も乗る。バイトだけ見ていると見落とす。

## 3. 既定値を疑う — PREDICTOR

`-of COG` を素で打つと `COMPRESS=LZW` が既定で付く。しかし UInt16 の連続値に
素の LZW はほとんど効かない。

| 版 | ファイルサイズ |
| --- | ---: |
| strip（無圧縮） | 72.0 MB |
| COG 無圧縮 | 101.7 MB |
| COG + LZW（既定） | 68.3 MB |
| COG + LZW + PREDICTOR=2 | **12.5 MB** |
| COG + ZSTD + PREDICTOR=2 + LEVEL=9 | **8.8 MB** |

`PREDICTOR=2` は隣接ピクセルとの**差分**を取ってから圧縮する。標高や輝度のように
隣が似た値を持つデータでは差分がほぼ 0 近傍に集まり、圧縮が桁で効く。

**「COG にした」で満足すると、まだ 5〜7 倍損している。**

### COG は容量を減らす技術ではない

無圧縮 COG は 72MB → **101.7MB に増える**。overview が元画像の
`1/4 + 1/16 + …` ≒ **+33%** を足すため。
トレードは **ストレージ容量 ↔ 転送量**で、S3 では egress の方が高いので合理的な交換。

## 4. S3 実測

ローカル HTTP での結論が実クラウドでも再現することを確認（`/vsis3/`）。

| S3 上のファイル | 窓512²(非整列) | 全域750×750 |
| --- | ---: | ---: |
| `sample_striped.tif`（68.7MB） | 6.193 MB / 3 req | 28.721 MB / 644 req |
| `sample_cog_zstd.tif`（8.4MB） | **0.167 MB** / 2 req | **0.246 MB** / **1 req** |
| 削減 | **37×** | **117×** |

## 5. 落とし穴メモ（GDAL 3.12.3 / AWS CLI 2.34 時点）

1. **`python -m http.server` は Range 非対応** — Range ヘッダを無視して `200` で全量返す。
   これで計測すると「COG にしても減らない」と誤結論する。`scripts/range_server.py` を用意した。
2. **GDAL の `/vsis3/` は SSO トークンを更新しない** — `aws` CLI は期限切れ後に refresh するが、
   GDAL は `~/.aws/sso/cache` の期限切れ `accessToken` を読んで失敗する。
   回避は `eval "$(aws configure export-credentials --format env)"`（鍵をファイルに書かない）。
3. **`GDAL_DISABLE_READDIR_ON_OPEN=EMPTY_DIR`** を付けないと、サイドカーファイル探索で
   余計なリクエストが出て計測がぶれる。

## 6. ベクター側（GeoParquet）との対応

`small_road_network_pipeline` の M3 タスク1 と並べると、同じ骨格が見える。

| | GeoParquet on S3 | COG on S3 |
| --- | --- | --- |
| 部分読みの物理 | HTTP Range GET | HTTP Range GET |
| 刈る最小単位 | row-group | 内部タイル |
| 統計・索引 | bbox covering 列 + min/max | IFD のタイルオフセット表 |
| 配置の前処理 | 空間ソート（Hilbert） | タイル化 |
| 解像度軸 | **なし** | **overview** |
| 効かせるための条件 | bbox 列述語を**明示的に書く** | 既定オプションを**疑って調整する** |

共通の教訓: **転送量はファイルレイアウトとクエリの書き方の両方が揃って初めて下がる。**
